Overall flow (how the system actually runs)
This is the same sequence used in production, presented in plain language.
1
Run the summary P&L at the selected level using that level’s native ID filter. This keeps formula accounts (Gross Profit, Net Income) accurate.
2
Pull the full customer list from dim_customers that matches the selection and any optional filters.
3
Fetch customer‑level transactions once for those customers and reuse that data to build District and Facility detail.
4
Generate headers (counts, census, headcount) and refresh counts after detail is built so totals match what you see.
5
Exclude facilities where Net Income is zero in both Current Month and the selected comparison period (YTD or QTD), so output focuses on active locations.
Performance note: Summary is queried at its native level; customer‑level data is used only for detail, not for rebuilding summaries.
What each tab does
A concise version of the real logic for each tab.

Subsidiary tab

1) Run subsidiary summary using subsidiary_internal_id (Month + selected comparison period: YTD or QTD). 2) Pull all customers in that subsidiary from dim_customers (optional region or district‑tag filter applies here). 3) Group customers into Regions and Districts. 4) For each Region, run a region summary using region_internal_id + subsidiary_internal_id. 5) Build District and Facility detail from the shared customer transaction set, with an optional checkbox to also apply the subsidiary filter to that detail.

Region tab

1) Run region summary using region_internal_id (optional subsidiary filter). 2) Pull all customers in that region from dim_customers. 3) Group customers into Districts. 4) Build District summaries and Facility detail from the same customer‑level transactions, and if a subsidiary filter is selected, only include transaction rows tagged to that subsidiary.

District tab

1) Pull all customers for the selected district (or district tag) from dim_customers. 2) Optionally narrow that report with a subsidiary filter. 3) Run the district summary using the matching customer transaction rows (Month + selected comparison period: YTD or QTD). 4) Build Facility P&Ls from that same filtered transaction set.

Facility detail

Facility rows are built from customer‑level transactions only. If Net Income is zero for both Current Month and the selected comparison period, that facility is excluded from the output and counts.

At a glance
Subsidiary summary by subsidiary ID → Region summaries by region + subsidiary → optional subsidiary filter on District + Facility detail
Region summary by region ID → optional subsidiary filter carries through District + Facility detail
District summary by customer list → optional subsidiary filter narrows transaction rows for summary + Facility detail
How filters are applied
Subsidiary filter: On the Region and District tabs, applies subsidiary_internal_id to summaries and to the detailed transaction rows. On the Subsidiary tab, the optional detail checkbox applies subsidiary_internal_id to District and Facility detail only.
Region filter: Applies region_internal_id to summaries and to the customer list pulled from dim_customers.
District tags: In the Subsidiary tab, a district tag limits the customer list to districts with that tag.
Process (Standard vs Operational): Controls which account rules are included in the P&L.
Example: Region = R870 + Subsidiary = Yona Ozark means the Region summary uses both IDs, and the District/Facility detail only includes transaction rows tagged to Yona Ozark.
How counts are calculated
Region count (Subsidiary tab): Regions included after filtering, and only if the Region summary has non-zero Net Income (Current Month OR selected comparison period).
District count (Subsidiary/Region tabs): Districts included only if the District summary has non-zero Net Income (Current Month OR selected comparison period), and only if that district is not marked “summary excluded.”
Facility count (all tabs): Facilities included only if Net Income is non‑zero (Current Month OR selected comparison period).
Counts are refreshed after detail is built, so headers reflect what you actually see in the output.
Census & headcount
Census: Rolled up from customer census records for the selected hierarchy.
Budget Census: Budget census is shown alongside actuals for comparison.
Headcount: Summed from census data for the selected customers.
Why rollups are accurate
Summary levels are queried directly by their native dimension filters, so formula accounts remain correct.
Customer‑level data is used only for District and Facility detail, never to rebuild Subsidiary or Region summaries.
This avoids the common issue where summing facility formulas would distort higher‑level totals.
